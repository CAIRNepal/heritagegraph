# Implementation Plan: YAML-driven schema, database, and UI form generation

**Branch**: `004-yaml-driven-schema` | **Date**: 2026-04-19 | **Spec**: `specs/004-yaml-driven-schema/spec.md`  
**Input**: Feature specification from `specs/004-yaml-driven-schema/spec.md`

## Summary

**Problem:** The LinkML ontology (`ontology/HeritageGraph.yaml` or repo-root `Heritagegraph.yaml`), the hand-maintained frontend `heritage_graph_ui/src/lib/ontology/registry.ts`, and Django `cidoc_data` models/serializers are three sources of truth that drift. That blocks reuse and forces triple edits for every class/slot change.

**Target:** Make the LinkML YAML the **only** edited ontology artifact. Add a **generation pipeline** (LinkML + custom emitters) that produces: (1) a **frontend-consumable registry** (same conceptual shape as today’s `OntologyClass` tree), (2) **JSON Schema** for client validation, (3) **server-side validation** metadata (and optionally Pydantic models) aligned with API writes, (4) **RDF URI maps** for export/sync. Add a **schema-serving API** (authenticated, versioned, cache-friendly) so the UI loads the registry at **runtime**, with a **checked-in generated snapshot** as CI/offline fallback. Keep **typed Django models** for existing CIDOC resources; add a **schema registry** table plus **dynamic/extension entity** storage for tenant-only classes. **Phase later:** write-through **RDF sidecar** (triplestore) for SPARQL/LOD, non-blocking on Django writes.

**Documentation (explicit scope for this plan):** Update repository markdown so contributors do not need to read source to extend the ontology — see [Related repository documentation](#related-repository-documentation-planned-updates).

## Technical Context

**Language/Version**: Python 3.13 (Django 5.2 + DRF 3.15), TypeScript / Next.js 15 (App Router)  
**Primary Dependencies**: **LinkML** (`linkml`, `linkml-runtime`) for parsing `SchemaView`, slot/class induction, and standard generators (`gen-jsonschema`, `gen-pydantic` as needed); **PyYAML** (already in repo); **jsonschema** (already in repo) for runtime validation hooks; **drf-spectacular** / **drf-yasg** for OpenAPI (existing). Frontend: existing `apiUrl` / `apiFetchJson` + NextAuth Bearer pattern.  
**Storage**: PostgreSQL (primary); Django models in `heritage_graph/apps/cidoc_data/models.py`; new tables for schema registry + dynamic entities; optional **JSONField** caches of merged ontology payloads. RDF sidecar: **not** in compose today — introduce as new service or defer to Phase P3 with clear interface.

**Testing**: `python manage.py test` for schema merge, permissions, and serializer validation; frontend unit/integration for registry loader + degraded fallback; contract tests against `contracts/openapi-schema-registry.v1.yaml` shapes.

**Target Platform**: Web (Docker / Traefik per repo conventions).

**Project Type**: Web application — Django API (`heritage_graph/`) + Next.js UI (`heritage_graph_ui/`).

**Performance Goals (align with spec SC-004 / SC-007):** Schema endpoint **&lt;200 ms p95** when served from memory/cache with unchanged version; RDF sync **&lt;60 s p95 lag** when enabled.

**Constraints:**

- New env vars (schema path, cache TTL, triplestore URL, feature flags) → **`.env.example`** only; no committed secrets.
- Frontend: **`NEXT_PUBLIC_*`** for API base URL; no new hardcoded production `localhost` URLs.
- Protected routes: **`Authorization: Bearer &lt;accessToken&gt;`** from NextAuth session.
- **Ruff** + **TypeScript build** on touched code.
- Backward compatibility: existing `/cidoc/` resource URLs and response shapes until versioned deprecation (FR-025).

**Scale/Scope:**

- ~50+ ontology classes, hundreds of slots (see `registry.ts` size today).
- Incremental delivery: **M1** generation + schema API + runtime UI loader; **M2** tenant extensions + dynamic CRUD; **M3** RDF sidecar + re-materialization job.

**Structure Decision:** Keep **generation scripts** under `tools/` (or `scripts/`) so Docker images can run them at build time without importing LinkML in the request hot path unless explicitly required. Prefer **in-process schema cache** in Django (load YAML once per worker + invalidate on version bump) for the schema endpoint performance target.
